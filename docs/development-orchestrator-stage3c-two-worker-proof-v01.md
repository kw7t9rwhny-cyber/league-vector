# Development Orchestrator Stage 3C — Two-Worker Autonomous Handoff Proof v0.1

## Status

Implementation candidate only. **Do not run the live agent chain before independent HIGH-risk QA PASS and separate Founder authorization.**

Authoritative architecture: Issue #52, Stage 3C Agent Execution Feasibility Report v0.1.

Fixture: Issue #53, `AGENT SPIKE TEST — harmless two-worker handoff`.

No production League Vector behavior is changed by this candidate.

## Objective

Prove this exact execution boundary after QA authorization:

```text
GitHub fixture state
  -> Stage 3C Research Worker A
  -> fresh Codex research execution
  -> durable GitHub Research comment
  -> GitHub workflow_run completion event
  -> Stage 3C QA Worker B
  -> fresh independent Codex QA execution
  -> durable GitHub PASS/FAIL comment
```

No Founder/Cody prompt copying or dispatch is allowed between Worker A and Worker B.

## Agentic Workflow sources

- `.github/workflows/stage3c-research-worker.md`
- `.github/workflows/stage3c-qa-worker.md`

The generated hardened representations are:

- `.github/workflows/stage3c-research-worker.lock.yml`
- `.github/workflows/stage3c-qa-worker.lock.yml`

The lock files must be generated by official `gh-aw` compilation and committed with the sources. They are not hand-authored.

## Engine and authentication

Both workers use:

```yaml
engine: codex
```

The repository Actions secret `OPENAI_API_KEY` is the only OpenAI authentication prerequisite for this proof. The secret is never referenced in workflow-level `env`, never printed, never persisted in an artifact/comment, never committed, and never requested from the Founder. The generated `gh-aw` runtime supplies engine authentication through its native secret boundary.

No PAT is introduced.

## Worker A — League Vector Research Worker

Trigger: Issue #53 is edited after the implementation is on the default branch, and the issue body contains the exact Stage 3C eligibility state `Eligibility: `READY``.

Additional activation guards bind the run to:

- Issue number `53`;
- exact fixture title;
- exact fixture revision `stage3c-v0.1-r1` checked by the worker;
- default-branch workflow source once merged.

Worker A receives repository and issue **read** permission only in the agent job. Its single permitted durable mutation is an `add-comment` safe output targeting Issue #53, constrained by title prefix and maximum one comment.

Required durable marker:

`STAGE3C_RESEARCH_RESULT v0.1`

The result correlates fixture revision, Research run ID/attempt, Research head SHA, source path, observed fact, and completion status.

## Durable handoff

Worker A's Codex conversation/session is non-authoritative and is never resumed by QA.

The authoritative handoff is the structured GitHub comment on Issue #53. Worker B accepts only a Research comment correlated to the exact `workflow_run.id` and `workflow_run.head_sha` that triggered it.

No agent artifact or hidden model state is required to carry the research conclusion.

## Worker B — League Vector QA Worker

Trigger:

```yaml
workflow_run:
  workflows: ['Stage 3C Research Worker A']
  types: [completed]
  branches: [main]
  conclusion: success
```

Worker B is a different Agentic Workflow definition and therefore a separate GitHub Actions run and fresh Codex execution. It does not resume Worker A.

Worker B reads Issue #53, finds the durable Research result correlated to the triggering Research run, independently inspects `docs/ARCHITECTURE.md`, compares repository truth with Worker A's claim, and emits exactly one safe-output QA comment.

Required marker:

- `STAGE3C_QA_RESULT v0.1 — PASS`, or
- `STAGE3C_QA_RESULT v0.1 — FAIL`.

## Permissions

### Worker A agent read boundary

```yaml
contents: read
issues: read
```

GitHub read tools are limited to repository/issues toolsets. Repository mutation is not exposed to the agent.

### Worker B agent read boundary

```yaml
contents: read
issues: read
actions: read
```

The `actions: read` scope allows QA to correlate the triggering Research run. GitHub read tools are limited to repository/issues/actions toolsets.

### Safe output write boundary

Each worker declares only one `add-comment` safe output, `max: 1`, targeting fixed fixture Issue #53. `gh-aw` performs safe-output writes in a separate permission-controlled job; the Codex agent itself remains read-only.

No merge, push, label change, issue edit, PR write, release, deployment, repository setting change, Founder decision, or production publishing safe output is declared.

## Cost bounds

Each worker is bounded to:

- `max-ai-credits: 250` per run;
- `max-daily-ai-credits: 500` per workflow;
- `timeout-minutes: 10`.

No agent is run during implementation/QA preparation.

## Concurrency and duplicate safety

Worker A uses one fixed concurrency group for fixture #53 with `cancel-in-progress: true` and a single pending slot. A newer duplicate eligibility edit cancels an older in-flight Research run; cancelled runs cannot satisfy Worker B's `conclusion: success` trigger.

Worker B's concurrency group is keyed to the authoritative Research workflow run ID. A given Research completion therefore has one serialized QA concurrency identity. The `workflow_run` trigger is additionally restricted to the exact Research workflow name, `main`, successful conclusion, same-repository/fork protections produced by `gh-aw`, and Worker B performs its own run-ID/head-SHA correlation before accepting the durable handoff.

Safe-output jobs are separately serialized on fixture-specific concurrency groups.

Retries remain bounded by GitHub Actions run attempts, the AI-credit/day caps, timeout, and one-comment safe-output maximum. A retry is not allowed to broaden permissions or spawn further worker types. This proof contains only A -> B; B has no downstream agent trigger.

## Stale-handoff rejection

Worker B must FAIL rather than accept evidence when any protected correlation is stale:

- Research marker is absent;
- Research run ID does not equal the triggering `workflow_run.id`;
- Research head SHA differs from `workflow_run.head_sha`;
- fixture number/title/revision differs;
- fixture is no longer `READY`;
- Worker A's claim disagrees with independent repository truth.

An older Research comment is never substituted for the exact triggering Research completion.

## Rollback / stop behavior

Before live proof, rollback is simply closing the implementation PR or reverting the Stage 3C workflow commit; no production behavior depends on it.

During a future live proof:

- Agent failure before safe output creates no authoritative Research/QA result.
- Research failure or cancellation does not trigger successful QA chaining.
- QA FAIL is durable evidence only; it performs no remediation, merge, deployment, or state transition.
- The fixture can be returned from `READY` to `DORMANT` to prevent new Research activations.

No automatic retry workflow is implemented in v0.1.

## Exact live proof procedure — NOT AUTHORIZED YET

After independent HIGH-risk QA PASS and separate Founder authorization only:

1. Confirm both `.md` Agentic Workflow sources and generated `.lock.yml` files are on `main` at the approved exact SHA.
2. Confirm Issue #53 still has fixture revision `stage3c-v0.1-r1` and `Eligibility: `DORMANT``.
3. Confirm the repository Actions secret `OPENAI_API_KEY` exists without reading its value.
4. Record the pre-proof comments and workflow-run state for Issue #53.
5. Edit only Issue #53, changing `Eligibility: `DORMANT`` to `Eligibility: `READY``. This is the one Founder activation action for the proof.
6. Do **nothing** between Worker A and Worker B.
7. Verify Research Worker A starts automatically from the issue edit.
8. Verify Research A is a Codex engine run and writes one `STAGE3C_RESEARCH_RESULT v0.1` comment.
9. Verify successful completion of Research A automatically creates a distinct QA Worker B run via `workflow_run`.
10. Verify QA B has a different workflow/run identity and fresh Codex execution, reads the durable Research comment, independently checks `docs/ARCHITECTURE.md`, and writes one PASS/FAIL marker.
11. Verify no production file, branch, model, UI, deployment, merge, release, or Founder-decision state changed.
12. Return Issue #53 eligibility to `DORMANT` after evidence capture if no further proof run is authorized.

PASS requires every criterion in the Founder authorization prompt. Any manual Founder/Cody action between A and B is a proof failure.
